# Field Capture Framework and Deployment Decision

## Recommended path

**Choose Expo with EAS Build + EAS Update, using the prebuild and development-build workflow, and plan from day one for one custom native Android printer module.** Do **not** use Expo Go as the project’s long-term runtime. Treat the PT-210 printer spike as the first gate, and keep iPhone printing explicitly uncommitted until the PT-210’s transport is proven. This recommendation is **high confidence** for the overall architecture, **high confidence** for Android-first execution, and **medium confidence** for eventual iOS printing because that depends on the printer’s actual protocol. citeturn20view0turn20view1turn37view1turn38search1turn40view0turn27search16turn27search7turn26search1turn28search12turn28search4

The reason this beats the alternatives is simple: Field Capture is a **hardware-heavy field app**, but it is still mostly a **forms, sync, camera, signatures, and role-based offline data** product. Expo’s official docs now clearly support **custom native code, config plugins, local native modules, real development builds, real store builds, and OTA updates**; React Native’s official site also explicitly frames the stack as one that can use “any library, SDK, or native code.” That gives a solo maintainer a single shared codebase for the majority of the app, while still leaving room to write the one piece of native code this project is most likely to require: the printer transport layer. citeturn20view0turn20view2turn20view3turn25search18turn34search6turn38search1turn39search6

The strongest counterargument is bare React Native. Bare RN **does** make direct hardware work somewhat simpler because you are no longer fitting native integration into Expo’s prebuild/config-plugin discipline. But Expo prebuild plus a local Expo module is close enough to bare capability that it is **not worth giving up** EAS Build, EAS Submit, EAS Update, and the smoother solo-maintainer workflow unless the printer spike proves Expo’s native-module path too awkward in practice. That makes **Expo prebuild/dev-client the best primary path** and **bare RN the best escape hatch**, not the default starting point. This is **high confidence**. citeturn20view0turn20view2turn20view3turn38search7turn39search0turn39search8turn39search21

## Why this path wins over the alternatives

The decision is driven less by generic “cross-platform” arguments and more by the specific mix of requirements: **offline-first, low-end Android devices, direct printer I/O, background sync, camera capture, signatures, future NFC, and real installable production distribution**. Expo already gives official support for camera, SQLite, task management, and update delivery; SQLite is persisted across app restarts, and background tasks are backed by Android WorkManager and iOS BGTaskScheduler. Those are exactly the boring-but-essential building blocks a field app needs. citeturn35search0turn36view0turn37view4turn37view1

Flutter is a credible second-place option for this project. Its plugin ecosystem does have solid entries for BLE, NFC, USB serial, background tasks, and SQLite-like persistence: `flutter_blue_plus` for BLE, `nfc_manager` for NFC, `usb_serial` for Android USB serial, `workmanager` for background work, and `drift` for SQLite-backed persistence. The problem is the printer-specific part of the stack. The **best-cited Flutter BLE package explicitly says Bluetooth Classic is not supported**, which matters because low-cost receipt printers frequently expose Classic SPP rather than BLE. Flutter _can_ talk to ESC/POS Bluetooth printers through packages like `esc_pos_bluetooth`, but those package choices are more fragmented and less reassuring for a “printer-first” architecture decision than an Android-native module built on official platform APIs. That makes Flutter **good overall**, but **not clearly superior** for this printer-gated project. This is **medium-to-high confidence**. citeturn29search1turn29search0turn29search2turn29search3turn30search0turn30search2

Native Swift + Kotlin is the strongest option **only if** the printer spike shows that Field Capture must live close to platform APIs for both platforms. Native Android can directly use RFCOMM/SPP sockets and USB host APIs; native iOS can directly use Core Bluetooth for BLE and ExternalAccessory for MFi accessories. But for a one-developer team, two full codebases would raise the long-term cost of every offline form, sync mutation, signature screen, auth flow, and backend contract change. Since most of Field Capture is shared business UI rather than highly custom device UX, the native-only path is **technically strongest** but **economically wrong** unless the PT-210 forces it. This is **high confidence**. citeturn27search16turn27search7turn26search1turn28search12turn28search1turn28search4

Kotlin Multiplatform is not the right primary path here. JetBrains now positions Kotlin Multiplatform as production-ready and Compose Multiplatform as stable for Android and iOS, but KMP still does not remove the hardest part of this problem: the printer and hardware layer still needs platform-specific implementation and debugging. KMP is most attractive when shared domain logic is the primary pain point; Field Capture’s first pain point is external hardware transport and deployment simplicity. That is why KMP is **interesting but misaligned** for this project. This is **medium confidence**. citeturn31search5turn31search3turn31search8

## Printer transport feasibility and the decision gate

The PT-210 spike is the correct first gate because Android officially supports **RFCOMM/SPP-style Bluetooth sockets** and **USB host mode**, while iOS printing feasibility depends on whether the device exposes **BLE** or is an **MFi accessory** that can be reached via ExternalAccessory. Android’s Bluetooth docs explicitly support establishing RFCOMM channels and transferring data, and Android’s BluetoothSocket docs call RFCOMM the common socket type supported by Android APIs and identify it as Serial Port Profile. Android’s USB host docs likewise confirm host-mode communication with attached USB devices. On iOS, Core Bluetooth is the BLE path, while Apple’s ExternalAccessory guidance states that framework access is only for accessories developed under the MFi program, including Bluetooth accessories. This is **high confidence**. citeturn27search16turn27search1turn27search7turn27search10turn26search1turn26search4turn26search19turn28search12turn28search0turn28search1turn28search4

That creates the central answer to the Expo questions. **Expo managed/prebuild/dev-client does not inherently block Android Bluetooth Classic SPP**, but **Expo Go absolutely is insufficient** because Expo says Expo Go can only access native libraries already included in the Expo SDK, while development builds allow custom native code and custom configuration. So if PT-210 requires RFCOMM/SPP, raw USB serial, a vendor SDK, or custom ESC/POS transport code, the Expo path is still viable, but it requires either a **local Expo native module** or a compatible RN native module, plus any required **config plugin** changes for permissions or manifest/plist edits. This is **high confidence**. citeturn20view0turn20view1turn20view2turn37view1

Bare React Native makes the printer integration somewhat easier because you write the native code directly without prebuild rules. Flutter also remains viable, especially for BLE or USB-serial cases, because the package ecosystem includes `usb_serial` and BLE packages, and there are ESC/POS printer packages. But Flutter’s best-cited BLE package explicitly excludes Bluetooth Classic, which matters a lot if PT-210 turns out to be SPP-only. Native Android and iOS would make hardware access easier still, but not enough to justify two codebases **unless** the PT-210 spike proves the printer protocol demands substantial native work on both platforms. This is **medium-to-high confidence**. citeturn29search1turn29search0turn29search3turn27search16turn26search1turn28search4

### Concrete module strategy

For the **recommended Expo path**, the right move is **not** to hunt for a magic printer package first. The right move is to implement a **small local Expo module** named something like `expo-field-printer`, with Android methods for: device discovery, connect, disconnect, reconnect, write raw bytes, query status, and cash drawer / cut / QR / image operations if the protocol supports them. Expo officially supports local native modules in Swift and Kotlin, and recommends config plugins for native project configuration instead of hand-editing generated files. That keeps the “Expo convenience” while isolating the risky hardware code in a replaceable seam. This is **high confidence**. citeturn20view0turn20view2turn20view3turn20view4

If you want candidate transport libraries for the spike phase, the most relevant verified ones from the sources reviewed are: `react-native-usb-serialport-for-android` for Android USB serial in RN, `react-native-bluetooth-classic` as an RN Classic Bluetooth option, `esc_pos_bluetooth` for Flutter ESC/POS over Bluetooth, `flutter_blue_plus` for Flutter BLE only, and `usb_serial` for Flutter USB serial. I would still treat these as **spike tools**, not architectural commitments, because the PT-210 protocol is still unverified. This is **medium confidence**. citeturn22view3turn23view0turn21search2turn29search0turn29search1turn29search3

### Hardware spike gate

The first Android spike should verify the following, in this order: discover transport, connect, print a plain-text ticket, print a bitmap signature, print a QR code, reconnect after app restart, reconnect after printer sleep, and recover after disconnect / low battery. The decision logic should be:

- **If PT-210 supports raw ESC/POS over Android RFCOMM/SPP or USB OTG**, keep the **Expo prebuild/dev-client** recommendation. Build a local Android native module and continue. **High confidence.**
- **If PT-210 supports BLE GATT cleanly and accepts printable commands**, keep the same recommendation and keep iOS printing on the roadmap. **Medium confidence** because BLE printer implementations vary.
- **If PT-210 is Bluetooth Classic SPP only and not MFi**, Android printing remains feasible, but **iOS printing with this printer should be considered blocked**. **High confidence.**
- **If PT-210 requires a separate vendor app and does not expose an embeddable protocol or SDK**, the printer fails the project. Replace the printer rather than contorting the app choice. **High confidence.**
- **If PT-210 uses a proprietary undocumented protocol with no stable transport hooks**, the framework should not change first; the **hardware choice** should change first. **High confidence.**

These gates follow directly from Android RFCOMM/SPP and USB support, Apple BLE vs ExternalAccessory/MFi rules, and Expo’s ability to add custom native code while still shipping real binaries. citeturn27search16turn27search1turn26search1turn28search12turn28search4turn20view0

## OTA and store reality

EAS Update is a **real OTA mechanism**, but it is not a loophole around store review. Expo’s docs say EAS Update works by separating the app into a **native layer** and an **update layer**; updates can only be delivered when the **platform** and **runtime version** match exactly, and runtime version changes are required when native changes alter the JS-native interface. In practice, that means JS code, assets, text, forms, some logic, and non-native bug fixes are fair game for OTA, but **printer modules, new permissions, native SDK changes, Info.plist/AndroidManifest changes, and native dependency changes require a new binary build**. This is **high confidence**. citeturn40view0turn38search1

Apple’s current App Review Guidelines remain the hard boundary: apps may not download, install, or execute code that introduces or changes app features or functionality. That is why any OTA system for iOS must stay within the line of updating the already-approved update layer rather than mutating the native app into a materially different product. So the practical rule for Field Capture is simple: **use EAS Update for same-runtime-version JS and asset hotfixes; use TestFlight / App Store submissions whenever native behavior changes**. This is **high confidence**. citeturn9view0turn9view2turn40view0

For bare React Native, the old mainstream answer, CodePush/App Center, changed recently. Microsoft’s official retirement notice says App Center retired on **March 31, 2025**, recommends store distribution for release/test distribution, and says they prepared a special version of CodePush that runs independently from App Center. That means CodePush is no longer the stable, default, low-friction answer it once was. Bare RN can still use EAS Update, including in existing native apps, but the cleanest OTA story among the paths evaluated is now the Expo/EAS route. This is **high confidence**, and it is one of the few facts in this report that changed materially in the 2025-2026 window. citeturn17view0turn39search8turn39search21

I did **not** find an official Flutter OTA path in the sources reviewed that is equivalent in maturity and first-party integration to EAS Update. Flutter distribution through the stores is straightforward, but for store-compliant OTA the same Apple rule still applies, and the official sources reviewed did not surface a first-party Flutter service comparable to EAS Update. So for this report, Flutter’s OTA posture should be treated as **weaker and less integrated**, not impossible. This is **medium confidence**. citeturn9view0turn9view2turn32search1turn32search20

## Recommended deployment strategy

### Apple account and iOS distribution recommendation

Use the **Apple Developer Program, Organization account**, and target **TestFlight for pilot distribution**, then **Custom App distribution through Apple Business Manager** for the internal workforce if the company can operate Apple Business Manager. Apple’s business distribution page explicitly distinguishes this route from the Enterprise program: the regular Apple Developer Program supports App Store distribution, **unlisted apps**, and **custom app distribution with Apple Business**, while the Enterprise program is a separate path for in-house app distribution through MDM. For a small internal workforce app, that makes **Organization + TestFlight + Custom App** the cleanest recommendation. This is **high confidence**. citeturn6view4turn6view0turn6view1

Why not Enterprise? Because Apple’s own distribution matrix places custom apps under the standard Developer Program and reserves Enterprise for in-house app distribution through MDM. For a small team and likely BYOD environment, the Custom App route is the more proportional choice. If Apple Business Manager is not practical, a secondary path is **Unlisted App distribution** under the regular Developer Program. Ad hoc distribution exists, but Apple itself frames it more as a limited/private sharing tool than as the best long-term workforce distribution model. This is **medium-to-high confidence**. citeturn6view4turn8view0

Operationally, use **internal TestFlight** for the owner and any company Apple IDs that are on the dev team, and **external TestFlight** for pilot users. Apple currently allows up to **100 internal testers** and up to **10,000 external testers**; external testers require App Review approval of the first build in the group. That is more than enough for a field workforce pilot and keeps the app fully “real” from the owner’s perspective. This is **high confidence**. citeturn6view0turn6view1

### Android distribution recommendation

Use **Google Play Internal testing** for developer/owner smoke testing and **Google Play Closed testing** as the primary worker distribution path on personal Android phones. Google’s official docs say internal testing is for up to **100 testers** and closed testing is for controlled tester groups you choose. For an internal workforce on BYOD phones, this is the best balance of install simplicity, automatic updates, and security without requiring MDM or managed company devices. This is **high confidence**. citeturn11view1turn11view0

Use **Managed Google Play private apps** only if the business later adopts Android Enterprise or an EMM/MDM. Google’s managed-play docs make clear that Managed Google Play is for organizations with managed accounts and curated enterprise app access, which is excellent for company-managed devices but usually too heavy for an early small-team BYOD rollout. So the exact Android recommendation **today** is: **Play Closed testing for workers**, with **Managed Google Play private app** as the later enterprise-grade upgrade. This is **high confidence**. citeturn14view1turn14view0turn14view3

I do **not** recommend APK sideloading or direct APK download as the primary steady-state method for field workers. They can work technically, but they give up the update reliability and trust path of the Play Store. For a one-developer internal app, that extra update friction becomes operational debt quickly. This is **medium confidence**, based mainly on practical operations rather than newly researched policy.

### Concrete build, sign, distribute, and update pipeline

The recommended pipeline is:

1. **Develop in Expo with development builds**, not Expo Go. Use Android development builds for the printer spike because Expo itself says development builds are the path when custom native code or custom native configuration is needed. citeturn20view0turn20view1
2. **Build Android and iOS with EAS Build**. EAS is explicitly positioned by Expo as the cloud path to build, submit, and update Expo and React Native apps. citeturn38search11turn38search0turn38search7
3. **Sign Android with Play App Signing** through the normal Play Console path; sign iOS through App Store Connect / TestFlight as usual. Google’s private app docs and release docs confirm Play Console production/testing flow, while Apple routes through TestFlight/App Store Connect. citeturn14view3turn11view1turn6view0
4. **Distribute Android dev builds to the developer via internal testing**, then field-worker builds via **closed testing link**. Distribute iOS builds via **TestFlight**. citeturn11view0turn11view1turn6view0
5. **Use EAS Update for hotfixes** that do not change the native layer. Use two channels, at minimum: `staging` and `production`. Expo’s update model formally supports channel/branch separation and exact runtime-version matching. citeturn40view0turn39search12
6. **Require a full rebuild and store submission whenever native code changes**. That includes printer-native code, any BLE/USB stack change, new native permissions, new config-plugin output, and any runtime-version bump. citeturn40view0turn9view2

In short, the distribution story the owner wants is fully compatible with the recommendation: **real installable builds, real TestFlight, real Google Play testing/distribution, and real OTA where OTA is actually allowed**. That requirement does **not** argue against Expo; it argues against **Expo Go as the product runtime**, which I am explicitly not recommending. citeturn20view1turn20view0turn38search1turn39search6

## Self-hosted backend implications

Field Capture talking to a locally hosted FastAPI server is architecturally fine, but the mobile app must behave like a hostile-network client, not like a same-LAN toy app. Apple’s business docs explicitly discuss connecting apps to **servers on a private network**, and Expo’s configuration/update model already assumes distinct build channels and app config for multiple environments. The right design is: `dev`, `staging`, and `production` server URLs in app config; LAN/VPN access when available; and an **offline-first local database that treats the server as sync authority, not as live session state**. This is **high confidence** for the broad direction. citeturn6view3turn34search6turn40view0turn36view0

For offline-first storage, use **SQLite as the primary local store**. Expo’s SQLite docs state the database persists across app restarts, which is what you need for cached role-specific payloads, queued field-ticket drafts, sync journals, signature blobs, and print retry state. On React Native, `expo-sqlite` works even in non-Expo RN apps when Expo modules are installed, which also protects the escape hatch to bare RN. This is **high confidence**. citeturn36view0turn34search6

For background work, do not design around “always-on background services.” Expo’s background-task docs are explicit that Android uses WorkManager and iOS uses BGTaskScheduler, that minimum intervals are constrained, that iOS decides when to run work, and that iOS task execution stops when the user force-quits the app. So background sync should be designed as **opportunistic reconciliation**, not guaranteed continuous daemons. High-value flows such as “field ticket saved,” “receipt captured,” and “signature completed” should sync immediately when online and queue durable retry work when offline. This is **high confidence**. citeturn37view4turn37view3turn37view2

For TLS and self-hosted access, the safest production posture is **public-trust HTTPS on a stable DNS name that resolves to the office/VPN endpoint**, not a raw self-signed cert pinned into the app. If private networking is unavoidable, prefer a managed private CA installed on company-managed devices over ad hoc self-signed exceptions. I was not able to pull all the platform-specific ATS / Android network-security references into this report before the finalization cutoff, so treat this recommendation as **medium confidence operational guidance**, not as a fully cited policy matrix.

## Final decision gate and escape hatches

The final recommendation stands **if the Android-first PT-210 spike proves one of these**: raw ESC/POS over Bluetooth Classic SPP/RFCOMM, BLE GATT with printable characteristics, or USB OTG serial/raw transport. In all three cases, the right implementation is still a **shared Expo app with a local Android native printer module**, because that keeps the app’s broad surface area cross-platform while confining hardware risk to a seam. This is **high confidence**. citeturn27search16turn27search1turn26search1turn20view0

If Expo hits a wall, the migration path is clean: **prebuild to native projects and continue as bare React Native**. Expo explicitly documents using EAS Update in existing native apps, and Expo SDK packages work in any React Native app with the Expo package configured. That means the escape hatch is not a rewrite; it is a workflow change and possibly some module refactoring. This is **high confidence**. citeturn39search8turn34search6turn20view0

If bare React Native hits a wall on the printer, the next step is not “rewrite the whole app native.” The next step is **promote only the printer stack into a dedicated native Android library/module**, keep the rest of the UI and sync engine in React Native, and expose a small stable JS interface. In other words, the escape hatch should be **native printer core, not native whole app**. This is **medium-to-high confidence**.

If iOS printing is blocked because the PT-210 is Bluetooth Classic SPP without MFi/ExternalAccessory support, do **not** contort the architecture to fake parity. Ship iPhone support for everything else only if that is still valuable, and separately qualify an iOS-compatible BLE or MFi printer for parity later. The app framework does not fix a printer that iOS cannot legally or technically talk to. This is **high confidence**. citeturn28search4turn28search1turn28search12

## Open questions and limitations

I was able to ground this report in current official Expo, React Native, Android, Apple, Google Play, Flutter/pub.dev, Kotlin, and Microsoft sources, but I was **not able to retrieve usable content from the selected GitHub repos during this session**, so this decision is based on platform and deployment evidence rather than repository-specific code reality.

The biggest unresolved item is still the **PT-210 protocol**. Until the hardware spike confirms transport and command compatibility, the iOS printing answer remains conditional. That uncertainty is **not** a framework weakness; it is the correct result of the hardware-first constraint you set.
